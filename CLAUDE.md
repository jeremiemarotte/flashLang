# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

`flashLang` is a self-hosted, agent-fed flashcard system for language coaching (English + Spanish,
target C1). The MVP described below (v0.1, spec dated 2026-07-11) is scaffolded and has been
smoke-tested end to end: migrations, card CRUD, dedup 409, per-token auth boundary, FSRS-driven
reviews, daily stats, and the PWA being served all work against a live `docker compose` stack.

## Commands

```sh
cp .env.example .env               # fill in POSTGRES_PASSWORD, HERMES_TOKEN, PWA_TOKEN (openssl rand -hex 32)
docker compose up -d --build       # builds api image, runs alembic migrations on boot, starts db/api/backup
docker compose logs -f api         # tail API logs
docker compose down -v             # stop and wipe local volumes (dev only — never on the TrueNAS host)
```

There is no separate "run tests" command yet — the backend has no test suite. Verify changes by
exercising the running API directly, e.g.:

```sh
curl -X POST localhost:8000/cards -H "Authorization: Bearer $HERMES_TOKEN" \
  -H "Content-Type: application/json" -d '{"type":"basic","front":"...","back":"...","language":"en"}'
```

New Alembic migrations: edit models in `api/app/models.py`, then from inside the `api` dir with
`DATABASE_URL` pointed at a running `db` container:
```sh
alembic revision --autogenerate -m "description"
```
(the initial schema, `api/alembic/versions/0001_initial.py`, was written by hand rather than
autogenerated — later migrations should use autogenerate against that baseline.)

## What this system is

Hermes (a self-hosted conversational coaching agent) creates flashcards automatically during
language-coaching sessions. A PWA on iOS lets the user review those cards on a spaced-repetition
schedule (FSRS) during commutes. No manual card creation in the PWA, no audio, no multi-user,
no Anki import — read [4.](non-objectives) below before adding scope.

### Non-objectives (MVP) — do not add without an explicit scope decision
- Manual card creation/editing in the PWA (read + review only)
- Audio/pronunciation cards
- Multi-user or deck sharing
- Review via chat (Telegram/Discord)
- Gamification (streaks, badges, leaderboards)
- Anki `.apkg` import/export

## Architecture (three components + infra)

**1. Backend API** — `api/app/`, FastAPI + SQLAlchemy + Alembic + Postgres.
- `models.py`: `Card` (type, front/back or text, language, context, source_session, tags, FSRS
  fields: `due`, `fsrs_state`, `fsrs_step`, `stability`, `difficulty`, `last_review`, `reps`,
  `lapses`) and `Review` (card_id, rating, reviewed_at, interval_days). `front_normalized` +
  a unique DB index on `(language, front_normalized)` enforce dedup at the schema level, not just
  in application code.
- `fsrs_engine.py`: wraps the `fsrs` package (v6, `Scheduler`/`Card`/`Rating`/`State`). Our own
  `Card` row is the source of truth; `apply_review()` reconstructs an `fsrs.Card` from our stored
  fields, calls `scheduler.review_card()`, then writes the updated fields back — the library's
  own `Card`/`ReviewLog` objects are never persisted directly. `reps`/`lapses` are maintained by
  us (the library doesn't track them), incrementing `lapses` only on `Rating.Again` (1).
  Default FSRS weights, no personalization yet (per PRD, deferred to v2 pending review history).
- `auth.py`: two static bearer tokens, `HERMES_TOKEN` and `PWA_TOKEN`. `require_hermes` guards
  card creation (`POST /cards`, `POST /cards/batch`, `GET /cards/recent`) — the PWA is
  read/review-only by design, and this is enforced at the dependency level, not just documented.
  `require_any_client` guards read/review endpoints. Don't loosen `require_hermes` to
  `require_any_client` without revisiting the "PWA never creates cards" non-objective.
- `routers/cards.py`, `routers/reviews.py`, `routers/stats.py`: `POST /cards`, `POST /cards/batch`,
  `GET /cards/due?lang=&limit=`, `GET /cards/recent?lang=&limit=` (backs the Hermes skill's
  `list_recent_cards`, not in the original PRD endpoint list — added because the skill needed it),
  `GET /cards/{id}`, `DELETE /cards/{id}`, `POST /reviews`, `GET /stats/daily`.
- `main.py`: mounts the PWA's static files at `/` via `StaticFiles` — API routers are registered
  first so their paths take precedence over the catch-all static mount.

**2. Hermes skill** — `hermes-skill/SKILL.md`, kept in this repo (versioned with the API it calls).
- Tools: `create_flashcard` → `POST /cards`, `create_flashcards_batch` → `POST /cards/batch`,
  `list_recent_cards` → `GET /cards/recent`.
- Trigger rules live in the skill prompt, not backend logic: create a card only when an error is
  corrected ≥2 times, vocab is explicitly requested, or something's flagged "à retenir". Cap 5
  cards/session — a quality gate. Prefer `cloze` for grammar-in-context, `basic` for raw lexicon.
  Always populate `context`. A 409 from the API means "already tracked," not an error — the skill
  should treat it as success, not retry.

**3. PWA** — `api/app/static/` (`index.html`, `style.css`, `app.js`, `sw.js`, `manifest.json`).
- Not a separate service — static files served by the `api` container itself via `StaticFiles`,
  same origin as the REST API.
- Vanilla JS, no bundler/build step. Single-page state machine in `app.js`: gate (token entry,
  since there's no login UI — the PWA token is entered once and stored in `localStorage`) → home
  (due counts by language from `GET /cards/due`) → review (reveal → rate, cloze parsed from
  `{{c1::...}}` syntax client-side) → summary.
- Offline: last-fetched due cards cached in `localStorage`; reviews that fail to POST are queued
  in `localStorage` and flushed on next load. Last-write-wins, no conflict resolution — this is
  intentional (mono-device, mono-user), don't build a merge strategy.
- `sw.js` only caches the app shell (the fixed file list); it deliberately does not intercept
  `/cards`, `/reviews`, `/stats` requests — API offline handling lives in `app.js`'s own
  cache/queue, not the service worker.

## Docker / TrueNAS deployment shape

`docker-compose.yml` at repo root, three services (`db`, `api`, `backup`), deployed on TrueNAS
SCALE as a **Custom App** (compose import), not through the app catalog — gives full control over
volume-to-ZFS-dataset mounts.

- **`api`**: builds from `api/Dockerfile`. `entrypoint.sh` runs `alembic upgrade head` before
  starting uvicorn — migrations are applied on every container start, not a separate manual step.
  Port published on the host (`${API_PORT:-8000}`) so it's reachable over the host's existing
  Tailscale install — no `tailscale` sidecar container, no tunnel/proxy container in this stack.
- **`db`**: `postgres:16-alpine`, named volume `db_data`.
- **`backup`**: `postgres:16-alpine` reused as a client image, running `deploy/backup.sh` (a
  `pg_dump -Fc` loop, once/day, 30-day retention) to the `backup_data` volume. Exists because
  TrueNAS snapshots alone don't give a portable SQL dump if the app ever migrates hosts — don't
  remove this in favor of "snapshots are enough."

`deploy/docker-compose.truenas.yml` is the TrueNAS-specific override: rebinds `db_data`/
`backup_data` from Docker-managed volumes to bind mounts under `/mnt/<pool>/flashlang/...` so the
data lives on paths TrueNAS itself snapshots. Deploy on TrueNAS with:
```sh
docker compose -f docker-compose.yml -f deploy/docker-compose.truenas.yml up -d
```
Local dev uses the base `docker-compose.yml` alone (Docker-managed volumes, no ZFS paths needed).

Hermes reaches the `api` container over LAN IP if co-located on the same network, otherwise over
Tailscale, using its own `HERMES_TOKEN`.

Repo layout: `api/` (FastAPI app + Alembic + PWA static assets), `hermes-skill/` (the skill
markdown), `deploy/` (TrueNAS compose override + backup script), `docker-compose.yml` +
`.env.example` at root.

## Key constraints that should shape implementation choices

- Volumetric target is deliberately small (2–5k cards, 50–100 reviews/day) — this rules out
  needing sharding/caching layers; don't over-engineer the API for scale it will never see.
  The volume target exists specifically to keep Notion/Airtable-style tools disqualified, not
  to justify infra complexity.
- Latency budgets: `GET /cards/due` < 200ms LAN; perceived tap-to-next-card < 500ms in the PWA.
- A submitted review must never be lost — this is why reviews go through a DB transaction and the
  PWA has an offline queue; don't simplify either away.
- Failure signal to watch for post-launch: >100 due cards backlogged means the PWA has too much
  friction or Hermes is over-generating — the fix is friction/generation-rate, not new features.
